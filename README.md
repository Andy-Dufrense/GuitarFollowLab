# 吉他跟弹识别

对着麦克风弹吉他，网页实时判断你弹对没有。纯本地、零依赖，不用 npm install。

## 启动

双击 **`start.bat`**：检查 Node → 起服务。**不会自己弹浏览器**，
窗口里会打印地址，自己复制到浏览器打开就行。

```
start.bat            起服务，不开浏览器
start.bat 1210       换端口
start.bat -o         顺便用 Edge / Chrome 打开页面
```

停止服务就关掉标题为 `Guitar Follow Lab - server` 的那个窗口。

> **为什么不自动开浏览器**：这台机器的 http 关联是 Internet Explorer，
> 而 IE 根本跑不了这个页面。就算加 `-o`，脚本也不会走系统关联，
> 而是自己去找 `msedge.exe` / `chrome.exe` 直接启动，找不到就打印地址，
> 绝不退回 IE。

## 麦克风为什么开不了

**这条最重要，先看这里。** 浏览器只在 **https** 或 **localhost** 下才给麦克风权限，
这是 W3C 的安全上下文规定，不是这个页面的限制。

| 情况 | 能不能拿到麦克风 | 原因 |
|---|---|---|
| 电脑上 `http://localhost:1209` | 可以 | localhost 被特殊对待，算安全上下文 |
| 手机上 `http://192.168.x.x:1209` | **不行** | 局域网 IP 走 http 不算安全上下文 |
| 手机上 `https://192.168.x.x:1210` | 可以 | 走 https，且证书被信任 |

另外，**这台电脑本身没有任何音频输入设备**（`Get-PnpDevice -Class AudioEndpoint`
只列出了 Headphones 和 S/PDIF 两个输出）。所以就算地址对了，电脑上也开不了麦克风——
得插一个 USB 麦克风或者带麦克风的耳机。

页面右侧有个「麦克风开不了？点这里看原因」，会直接告诉你当前是哪种情况：
安全上下文、接口是否可用、检测到几个输入设备、上次报错的具体名字。

### 手机上点了「开始」没反应

按可能性从高到低排：

1. **你用的是 `http://192.168.x.x:1209`。** 这个地址浏览器不给麦克风，
   页面会提示但不会弹授权框。得走 https（见下面步骤）。
2. **站点权限被设成了「拒绝」。** 这个最阴——https 正常、证书也装了，
   但只要你之前点过一次拒绝（或者勾了"不再询问"），浏览器**以后都不再弹框**，
   直接拒绝。表现就是"点了开始，一直没弹框"。
   两个地方都要查：
   - 浏览器里：地址栏左边的图标（锁 / 盾牌）→ 权限 / 网站设置 → 麦克风 → 允许
   - 手机系统：设置 → 应用管理 → 找到这个浏览器 → 权限 → 麦克风 → 允许

   页面会把这条查出来告诉你（读的是 `navigator.permissions`）。
   **换个端口等于换了个站点，权限会重新问一次**：跑 `start.bat 1211`，
   手机改开 `https://<IP>:1212`。这一招只解决浏览器里那条，解决不了系统层。
3. **系统层面把麦克风关了。** 权限状态还是「询问」但请求被直接挡掉，
   说明是系统关的：安卓看 设置→应用→你的浏览器→权限→麦克风；
   iPhone 看 设置→Safari→麦克风。
4. **用的是手机自带浏览器。** 国产 ROM 的自带浏览器对 Web Audio 和麦克风的
   支持经常缺斤少两，而且默认就把自己的麦克风权限关着。
   最省事的办法是换 **Chrome / Edge** 打开同一个地址，证书不用重装。
5. **https 开了但没装证书**，你在警告页点了「继续前往」。
   证书没被信任时 Chrome 仍然不给麦克风。先按下面第 3 步装证书。
6. **你是在微信/QQ 里打开的链接。** 内置浏览器普遍不给麦克风，
   页面脚本有时也跑不起来。点右上角「⋯」→「在浏览器中打开」。
7. **浏览器太旧。** 页面用了 ES module，需要 Chrome 61+ / Safari 11+。
   页面停 2.5 秒还没启动就会自己报「页面没能启动」并显示浏览器 UA。

不管是哪种，页面都不会再"静悄悄没反应"：失败时右下角的说明会自动展开并滚过去，
里面写着当前的安全上下文、设备数量、上次报错名字和浏览器 UA。

### 手机上怎么用

有两条路，**安卓走第一条，不用装证书**：

**办法一：安卓 + Chrome flags（最简单）**

1. 手机 Chrome 地址栏输入 `chrome://flags/#unsafely-treat-insecure-origin-as-secure`
2. 那一项改成 **Enabled**，下面的输入框里填 `http://192.168.0.81:1209`
3. 按提示重启浏览器
4. 还是用 `http://192.168.0.81:1209` 打开，麦克风就能用了

**办法二：装证书走 https（iPhone 只能用这个）**

1. 电脑上双击一次 **`make-cert.bat`** 生成证书（已经生成过了，含 `192.168.0.81`）
2. 手机上打开 `http://<电脑IP>:1209`，在诊断面板里点「下载证书 local.cer」
3. 把证书装进系统
   - 安卓：设置 → 安全 → 加密与凭据 → 安装证书 → **CA 证书**
   - iPhone：装完后还要去 设置 → 通用 → 关于本机 → 证书信任设置 里打开完全信任
4. 用 `https://<电脑IP>:1210` 打开

证书是自签名的，只在这台电脑上有效，10 年后过期。

## 五个模式

## 节拍器（调灵敏度用）

右侧面板里有节拍器：BPM 滑块 + 起停 + 四拍指示灯。**跟着它弹，它会告诉你每个音偏早/偏晚多少毫秒**，
下面还会显示最近几次的列表、平均值和抖动。

- **不出声**（默认）：只有四拍指示灯闪。这样最干净，麦克风不会收到节拍器的响声。
- **出声**：用同一个音频时钟排拍子，重音在第一拍。但**响声会被麦克风收到**，可能触发误判，
  所以开了声音就戴耳机。
- **六线谱上没法对齐**——节拍器只有在麦克风开着的时候才能用，因为两者共用同一个音频时钟。

### 跟着 BPM 自动调参数

勾上「跟着 BPM 自动调参数」之后，判定等待和最小间隔会跟着 BPM 走
（按八分音符估算，快曲子自动缩短）。面板上会实时显示算出来的值，方便你对着调。

这个开关就是"根据 BPM 调整灵敏度"的第一步：显式、可解释，你能看到它把参数改成了多少。

## 变调夹

「高级设置」里有变调夹滑块（0~7 品）。夹上之后：

- 所有目标音高整体上移几度，页面上的目标音名和频率也会跟着变
- 和弦识别会跟着转调（观测到的音级转回来再和模板比）

## 踩过的坑（都表现成"某些音过不去"）

**1. 不能在滞后域里猜八度。** 曾经加过一条修补：如果 τ/2 处的差分值也不差，
就把音高翻倍，用来修"看低一个八度"。结果真实吉他拨弦的二次谐波常常比基频还强，
这条判据被骗，**六弦空弦 E2(82Hz) 被读成 E3、四弦空弦 D3(147Hz) 被读成 D4**。
一弦空弦 E4(330Hz) 同理会被翻成 E5——**E2 / D3 / E4 这三根正好就是被它读错的那三根**。

现在八度归属交给上层用频谱判，判据只有一条：**低八度那个音的基频到底存不存在**。
存在 → 实际就是低八度那个音；不存在 → 实际是高八度那个。这一条同时覆盖四种情况
（目标低弹低了 / 目标低弹高了 / 目标高弹低了 / 目标高弹高了），而且不会让 A2 冒充 A3——
A2 的二次谐波虽然正好落在 A3 的基频上，但这里查的是"110Hz 存不存在"，跟 220Hz 无关。

（试过用"某个频率上是不是一个峰"来区分，走不通：实测 A2 的二次谐波在 220Hz 处
是个比基频还尖锐的峰，突出度 4275 —— 谐波本身就是峰。）

**1b. 想靠低通压掉亮音色的偏高，代价太大。** 琴弦有刚性，高次谐波比整数倍略高，
音色亮的时候 YIN 会被这些偏高的谐波带着走，实测一弦那种音色偏高 25~30 音分。
试过在 YIN 前面加低通压高频——亮音色确实好转（降到 10 音分左右），
但**在"上一个音还在响"的混合信号里，低通会把相位关系搅乱，把 A3 直接判成 D2（差 3 个半音）**。
3 个半音的错比 25 音分的偏移严重得多，所以低通这条路放弃了。
残留的那点偏高在 50 音分以内，按音名判定本来就是通过。

**1c. 正确答案：不在时域里修，用频谱把音高修回来。** 上面那条"50 音分以内"是错的。
把非谐性系数调到真实钢弦量级（B≈0.0008）再测，偏差是 **+58 音分**——
正好越过 50 音分那条线，一取整就变成隔壁那个半音，判定成"高了 1 个半音"，永远过不去。
**这就是"一弦空弦 E4 总过不去"的根因**（一弦最亮，偏得最多；六弦 E2 也一样会中）。

修法很简单：琴弦刚性把第 k 次谐波抬高的量随 k 增大，但**基频几乎没被抬高**。
所以 YIN 给个粗估计之后，去频谱上找那个基频峰的位置，用它当结果。
搜索范围限制在 YIN 估计的 ±1 个半音内——找太远会跳到某个谐波上。

效果：

| 音 | 修正前偏差 | 修正后偏差 |
|---|---|---|
| 一弦空弦 E4（亮音色） | +25 音分 | **+0.7 音分** |
| 二弦空弦 B3（亮音色） | +30 音分 | **-0.7 音分** |
| 六弦空弦 E2（B=0.0008） | +58 音分 | **-1 音分** |
| 四弦空弦 D3（B=0.0008） | +54 音分 | **0 音分** |

**1d. 根本的改法：不再"先测音高再比对"，改成"候选音谐波比较"。**

前面 1~1c 全是打补丁，因为路子本身有问题：**用"开集单音检测"（YIN 问"这是什么音"）
去处理一个复音信号（几根弦同时在响）**。而这个绝对值会被音色、麦克风频响、
琴弦刚性、房间一起带偏——**换个用户、换把琴就未必成立**。

现在的做法是反过来。既然知道谱面上该弹什么，就不必问"这是什么音"，只问
**"新出现的这坨能量最像哪个候选音的谐波结构"**：

1. **逐频点本底**（`updateBackground`）：上升慢、下降快，把"已经在那儿的能量"
   （也就是余响）吸进去，剩下的就是新出现的。这只依赖"衰减只会往下走、
   新拨会往上跳"，跟音色无关。
2. **对候选音做谐波打分**（`matchNoteByCandidates`）：目标音和它的常见错法
   （±1、±2、±5、±12 半音）用**同一个**打分函数比一遍，谁高就是谁。
   系统性偏差对所有候选同等影响，一比较就抵消。
3. **不用知道琴弦刚性**：几个系数都试一遍取最好，而不是猜一个。

顺带解决了两个以前要专门打补丁的事：

- **八度不用特判**：弹 A2 时，A3 这个候选只能命中它的一半谐波
  （110、330 那些奇数谐波它没有），分数天然低一截。
- **音准偏差会说实话**：偏差近半个音时目标音和隔壁半音打成平手，
  这时提示"先调弦"，而不是靠四舍五入蒙混过去。

**验收标准是音色无关性**（`test-bughunt.mjs` 的 G 组）：
同一段 T3231323，用五种完全不同的音色渲染，必须全部通过——
理想弦、亮音色、**基频只有 10%（手机麦克风常见）**、强非谐性（B=0.0015）、闷音色。

**2. 环境噪声和延音。** 起音判据是"电平比 48ms 前抬升 1.6 倍"，基准窗不能缩短——
缩到 32ms 会让判定点提前，反而更容易被上一个音的余响带偏（实测 120BPM 会因此挂掉）。
所以灵敏度靠门限管：门限 = 噪声地板 × 4，绝对下限 0.0035。面板上调「起始灵敏度」即可。

**2b. 只看电平抬升，会被"延续不消音"拖垮——这是实测出来的关键一条。**
你让音一直响着，几根弦的余响叠起来的总电平可能比新拨的那一下还响，
抬升比例就上不去，于是触发不了。表现就是：
**弹完就消音 → 很丝滑；一直延续着弹 → 很迟钝。**

解法是不再看总电平，改看**频谱通量**：这一帧比上一帧"新增"了多少频谱成分。
余响只会衰减、不会凭空产生新成分，新拨一下则会在它自己的谐波位置冒出一整套新峰。
通量再配合一点点电平抬升（真拨弦一定会抬高电平，衰减中的余响永远不会），
两条一起用，延续不延续都一样灵敏。窗口取 2048 点（43ms）——取 512 点频谱太粗，低音弦分辨不出来。

**3. 环境噪声会糊掉和弦指纹。** 噪声是宽带的，在每个音级上都垫一层底。
现在维护一份**本底噪声谱**（每个频点取"缓慢上升、立即下降"的最小值，会自己贴到环境噪声上），
算和弦指纹之前先把它减掉，留下的才是琴声。电平条上会显示当前估到的「环境噪声」，
可以据此判断是不是环境太吵。

和弦判定之后还会额外压 100ms 静默期：和弦的余响又长又响，几根弦之间的拍频让音量忽高忽低，
很容易被当成"又扫了一下"。

| 模式 | 内容 | 判什么 |
|---|---|---|
| **单音** | 空弦六音 / 小星星 | 逐个音判音高 |
| **技巧** | 滑音 / 击弦 / 勾弦 / 推弦 / 泛音 | 屏幕上方会用大字标出这是哪个技巧，滑音只判落点 |
| **和弦** | Em / Am / C / G，每个弹一整段 T3231323 | 八个音按顺序逐个判，乐句条会显示走到哪一步 |
| **扫弦** | 一个和弦扫四下 | 每次扫弦判一次和弦指纹 |
| **转换** | C → G → Am → Em 连续换 | 看它能不能跟上你的和弦切换 |

T3231323 里的 `T` = 拇指，弹根音所在的那根弦；3/2/1 = 第三弦/第二弦/第一弦。
Em 的 T 是六弦空弦 E2，C 的 T 是五弦三品 C3。

弹对了自动进下一个，弹错了停在原地让你重弹，认不出来会说"没听清"而不是硬判成错。

## 识别是怎么做的

### 速度：一个音要多久

判过一个音到准备好听下一个音，中间的固定开销是 **60ms**（起音到测量的等待）。
判定结果只停在显示层，不挡流程——弹对了立刻就能往下一个音走。

```
起音 ──60ms──> 测量判定 ──立刻──> 下一步就绪
```

60ms 是个折中：拨弦的起振要稳定下来才测得准，但等太久就跟不上快曲子。

另外**起音那一瞬间目标音就会闪一下**（黄色），不用等判定出来才知道"它听见了"。
判定结果出来之后再闪绿或闪红。人耳对"没有即时反馈"的感觉很灵敏，
所以这一下即时反馈比压缩那几十毫秒更管用。

判单音时**不计算 Chroma**。算一次 Chroma 要做 61 个音高 × 5 次谐波查表，
只有判和弦才用得上，判单音时开着纯属白算白等。

**实测（Em 的 T3231323，八分音符连续八个音）：**

| BPM | 八分音符间隔 | 结果 |
|---|---|---|
| 60 | 500ms | 整段通过 |
| 80 | 375ms | 整段通过 |
| 100 | 300ms | 整段通过 |
| 120 | 250ms | 整段通过 |
| 140 | 214ms | 第 6 个音开始出错 |
| 160 | 188ms | 第 4 个音开始出错 |

极限出在 120~140 BPM 之间（八分音符 250ms）。再快就有一个物理问题：
上一个音还没衰减掉，几个音叠在一起，波形根本不周期，通用音高检测测不出来。

对付这个用了一招"频谱差分"：把起音之前的短窗频谱减掉，剩下的近似就是刚弹的这个音，
然后问"这坨新出来的能量更像目标音，还是更像它旁边那几个音"。
这是"知道标准答案"的直接好处——不需要回答"这是什么音"，只需要回答"是不是谱上要的那个"。
差分必须用**短窗**：两个 341ms 的长窗之间只差一百多毫秒，内容大部分重叠，
相减会互相抵消，差分出来是零（这个坑踩过）。

再往上提速就不是调参数的事了，得换架构：按弦分别跟踪，而不是把整个信号当成一个音。

和弦类（扫弦、和弦识别）要等 **300ms**，因为音级指纹需要 341ms 的分析窗
（低音弦的音级分辨率决定的，窗短了低音会差一个半音）。
想做到"实时的和弦跟踪"，得改成滑动 Chroma + 和弦变化检测，
不能一次一个和弦地等窗口填满。

### 两个踩过的坑（都会表现成"弹对了却不往下走"）

**起音检测不能要求"先彻底安静下来"。** 最早的写法是"电平掉到门限的 0.6 倍以下
才允许下一次触发"。只要上一个音还在响、或者房间底噪偏高，后面弹的音就永远
触发不了——界面上"听到"还在实时更新，但判定根本不跑。
现在改成：电平过门限，**并且高于最近 500ms 内的最高电平的 1.5 倍**。
窗口取 500ms 是有讲究的：几根弦之间的拍频会让余响忽高忽低，只有把上一个音的
"起音峰值"包在窗口里当基准，才压得住这些起伏。

**音高检测落在搜索边界上时不能采信。** 上一个和弦还在响、新音又进来的时候，
归一化差分函数会在最长的那个滞后上凑出一个假极小值，读出来就是"刚好 65Hz"，
判定成"听到 C2，比 E2 低了 4 个半音"。现在这种边界值一律当作没听清，
宁可说没听清，也不报一个假音高。

```
麦克风 → AnalyserNode 取 16384 点时域（48k 下 341ms）
       ├─ 末段 1024 点算电平 → 起音检测（自适应噪声门限 + 迟滞）
       ├─ 降采样到 12kHz
       ├─ YIN 自相关 → 单音音高（窗 1024 点，搜索 65~1400Hz）
       └─ FFT 4096 点 → Chroma 音级指纹 → 和弦模板比余弦相似度
```

三个当初调了很久才对的点：

**1. 低音区必须用长窗。** 12kHz 采样下 1024 点 FFT 的 bin 宽是 11.7Hz，
而 A2=110Hz 处一个半音才 6.5Hz——低音弦会直接差一个半音（A2 被认成 G#2）。
现在用 4096 点、341ms 的窗，bin 宽 2.9Hz 才够。

**2. Chroma 不能按频率 bin 累加。** 那样每个音级都会分到能量，12 个音级全亮，
Em 会被认成 Am。要反过来问：假设某个音级存在，它的第 1~5 次谐波位置上有没有能量。

**3. 和弦比对用余弦，不用集合重合。** 吉他和弦的泛音会让个别音级虚高，
集合类的度量一漏一多就掉得很快，余弦对这种溢出宽容得多。

另外只判原位和弦：Em/Am/C/G/D/Dm/G5 的音级集合互不混淆。
C 和 C/G 的音级集合完全一样，只有低音不同，要分开必须额外估低音——
而低音估计会被扫弦顺序带偏（先拨的弦衰减得最多）。

## 检测能力：2026-09-20 这一轮改了什么

原则没变：**先在测试里复现，再动代码**。三个真实场景都写进了 `test/test-detect.mjs`。

| 现象 | 复现 | 根因 | 改法 |
|---|---|---|---|
| 先扫 C 和弦，再弹六弦空弦 E2 → 判成"高一个八度"（E3） | B 组（原始信号 + 手机麦克风各一遍） | 老打分函数只问"该有能量的地方有没有能量"，从不问"该有的地方缺了没有"。E3 的谐波正好是 E2 的偶数次谐波，而 C 和弦里的 E3/E4 又刚好落在那里 —— 它蹭到的还全是权重最高的低次项 | 换成**双向失配**（Two-Way Mismatch）：预测的谐波没找到要扣分，观测到的峰解释不了也要扣分。两者都用音分计 |
| 判错之后，接下来 300ms 弹的音**完全听不见** | B 组时间线：只有 416ms 那一次判定（是 C 和弦自己），1.6s 那次拨弦压根没触发 | `retry()` 用 `setTimeout(300ms)` 才把相位放回 waiting —— 判错一次就等于把耳朵关 300ms。密集连弹（120BPM 八分音符 = 250ms 一个音）必然踩中 | 判错**立刻**恢复监听。防止余响重复触发是起音检测的职责，不该由一个固定闸门兼职 |
| "低一个八度"的候选（E1）跟真音打平 | `probe-octave.mjs` 的排名表 | E1 把 E2 的每个谐波都当成自己的偶数次谐波，余响一多就跟 E2 打平 —— 可 E1 在这把琴上根本弹不出来 | 候选按**乐器音域**过滤（最低空弦 → 最高 24 品），弹不出来的音不当候选 |
| 偏低近半个音时报了个不相干的音（F#2） | `test-live.mjs` 第 2 组 | 失配超过 40 音分的部分被一律截断，"差 48 音分"和"差 246 音分"分不出来 | 封顶放到 150 音分；另外加"音准扫描"：把目标往 ±¼、±½ 个半音挪一下，如果明显更像 → 说"弦没调准，先调一下"（既不放过去，也不说弹错了） |
| 显示层对和弦事件也跑单音判定（拿 undefined 当目标） | 重构后暴露成崩溃 | 历史遗留：和弦事件没有 targetMidi | 显示分支只在单音事件跑；判定函数自己也做了兜底，不再假设"一定有候选" |

**改完的实测数据**

| 场景 | 改前 | 改后 |
|---|---|---|
| 安静环境单独弹 E2 | 目标和低八度打平（领先 1.00 倍） | 领先 1.6 倍 |
| C 和弦余响中弹 E2 | 判成 E3（差一个八度） | 领先 1.2~1.4 倍，判过 |
| 手机麦克风频响（低频高通）+ 六根空弦，间隔 450ms / 700ms | 未测 | 都整段通过 |
| 完全不消音 + 手机麦克风，T3231323 @ 60/80/100 BPM | 未测 | 都整段通过 |
| 音色无关性（5 种音色，验收标准） | 通过 | 通过（没退化） |
| 判定耗时 | — | 0.11 ms/次（`probe` 量出来的，可以忽略） |

诊断脚本（想看数字就自己跑）：

## 为什么是纯 JavaScript（别的产品用什么）

这个项目到目前为止**一行 Python 都没有**：浏览器里 JS 管采集、分析、判定、界面，Node 只当静态文件服务器。
这是刻意的选择 —— 手机麦克风只能在安全上下文里拿到，算法贴着麦克风跑就省掉一次上传，延迟也最低。

行业里的分工大致是三层：

| 层 | 用什么 | 例子 |
|---|---|---|
| 实时判定 | **原生代码**（C++ / 平台原生），不是脚本语言 | Yousician 的 GitHub 组织里是 JUCE（C++ 音频框架）、RxCpp、Unity 原生插件 —— App = Unity + 原生 C++ 音频引擎；Rocksmith 系列是游戏引擎里的原生实现；Simply Piano / SmartMusic 同样是原生 App |
| 离线 / 内容侧 | **Python** 为主 | Yousician 研究者的论文（arXiv:2510.05756，用分轨 + MERT 转写吉他节奏型）代码是 Python；我们 VirtuCoach 后端也是 Python |
| 开源 Web 端 | 也能在浏览器跑 Python | MIT 的 web-score-following 就是用 Pyodide 把 Python DSP 搬进浏览器 —— 代价是体积和启动时间，只有需要现成科学计算库时才划算 |

所以结论是：**实时链路没必要换语言**；真正需要 Python 的地方是两件事 ——
① 离线评测与标注（librosa / madmom / mir_eval 那一套）；② 真要上神经网络时的训练和导出（导出成 ONNX/TFLite 再给前端跑）。

### 分层与依赖方向

```
main.js  ← 只做调度：读一帧 → 分析层 → 判定层 → 界面层
  ├─ analysis.js  → dsp.js, config.js
  ├─ judge.js     → state, analysis, ui, dsp, metronome
  ├─ metronome.js → state, ui, audio
  ├─ ui.js        → config, state, audio
  ├─ audio.js     → config
  └─ state.js     → config, exercises
```

依赖单向，没有环。浏览器原生支持 ES module，**拆完依然不需要任何构建工具**，
双击 `start.bat` 就能跑。

几个边界是刻意划的：

- **算法不认识界面**：`analysis.js` 里是纯函数，上层给 buffer，它还结果；
  它自己的跨帧状态（噪声谱、上一帧频谱）自己管，不往共享状态里塞。
- **界面不做判定**：`ui.js` 只管把状态画出来。
- **判定策略集中在 `judge.js`**：单音的音名比对、八度归属、频谱差分兜底、
  和弦指纹比对、听不清时的补测顺序，全在一个文件里，改判定不用翻别处。

> **踩过的坑**：拆完之后测试开始互相污染。原因是状态搬到了 `state.js`，
> 而测试用 `?case=X` 只让入口重新加载，`state.js` 是共享的。
> 这也暴露了缺一样东西——应用需要一个正式的复位入口，于是补了 `resetApp()`。
> 但 `CFG`（用户设置，比如变调夹）它**不清**：真实使用中你换过变调夹，
> 复位练习进度不该把它清掉。测试要自己记得归零。

跑测试（**五个都必须退出码 0**）：

```
node test/test-dsp.mjs
node test/test-live.mjs
node test/test-detect.mjs
node test/test-mic-fail.mjs
node test/test-bughunt.mjs
```

## 音高表

标准调弦 **EADGBE**（不是 EADBE，那是少了一根弦的写法）：

| 弦 | 空弦音 | 频率 |
|---|---|---|
| 六 | E2 | 82.41 Hz |
| 五 | A2 | 110.00 Hz |
| 四 | D3 | 146.83 Hz |
| 三 | G3 | 196.00 Hz |
| 二 | B3 | 246.94 Hz |
| 一 | E4 | 329.63 Hz |

品 n 的音高 = 空弦音 + n 个半音；加变调夹整体再升 capo 个半音。
但推弦 / 滑音 / 泛音 / 闷音 都不服从这个规则
（12 品自然泛音是空弦音升八度，不是升 12 个半音，所以页面上泛音是单独标出来的）。
